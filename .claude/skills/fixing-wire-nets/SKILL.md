# 修正線路網辨識（畫線）

## 核心原則
接線單元匯出檔裡的每個單元，都是人工認定的同一條線，**驗收標準是每個單元只落在 1 段線路網**。遇到斷點，一定先放大原圖看清楚是哪種圖面結構，再依下表選修法。只靠座標距離推測接點會出錯，例如看起來相距 0 px 的交叉點，其實是沒有圓點的純交叉。

**不適用的情況**：如果原圖本身要改，例如換元件符號、加線或刪線、改字，改用 **REQUIRED SUB-SKILL:** `editing-diagram-image`；改完再回到這裡驗收。

## 流程
以下路徑都相對於專案根目錄。`$S` 代表 `.claude/skills/fixing-wire-nets/scripts`。
1. **找斷點**：`node $S/verify.js` 會列出非 1 段的單元。再用 JSON 內各段的 `segments` 算出兩段最近的端點，就是斷點座標。
   - 新匯出的檔案每個單元多半只有 1 個 pick 點，`verify.js` 會全部 PASS、抓不到使用者回報的斷點。這時在回報位置的兩側各取一點，用 `node $S/acceptance.js 左x,左y=右x,右y` 確認確實斷開，修完再用同一組點驗收。
2. **看原圖**：`node $S/crop.js <out.png> x y [半徑] [倍率]`，再用 Read 看圖，對照下表分類。
   - 分不清是哪種結構時，跑 `node $S/labels.js x0 y0 x1 y1` 看斷點：
     - 斷開處的筆畫標成 `#`，表示根本沒偵測成線段，多半是太短（短於 `minRun`）或太細。
     - 斷開處有線段編號、只是兩邊編號不同，表示偵測到了卻被排除或沒判成相連，例如「ㄈ」轉折被當成框線、圓點偏離。
3. **修**：
   - 改之前先記下基準：`BASE=$(git stash create); BASE=${BASE:-HEAD}`。這會把目前工作區（含還沒 commit 的修改）存成一個 commit，不動到檔案；工作區乾淨時就用 `HEAD`。每個指令各開一個 shell、變數不會保留時，先 `echo $BASE`，之後直接寫那個 commit 編號。
   - 依分類修改 `js/nets.js` 的參數，或 `data/<圖>/fixes.js` 的 `dots`／`links`／`cables`。
   - 要還原時用 `git restore js data/<圖>`（基準是快照時，改用 `git restore --source=$BASE js data/<圖>`）。
4. **查副作用**：`node $S/verify.js $BASE`。
   - 參數可以是 git ref，也可以是資料夾。git ref 會用 `git archive` 把當時的 `js/` 和 `data/<圖>/` 取出來當「修改前」，規則、人工修正、線色標註和底圖的改動都會一起比對。
   - 每筆「新合併」會印出「接點」：被併在一起的舊線路網之間最近的位置，直接拿去 crop。
   - 想確認某個早就存在的修正有什麼效果，可以複製一份專案、把該修正拿掉，把這個資料夾當成基準傳進去。
   - 「新合併」比對的是全圖，不限接線單元。
   - 沒有接線單元檔的圖（例如 PA12C）、只改了 `anchors.js`、或改了底圖時，用 `node $S/diff.js $BASE`。它以座標逐段比對，列出線色改變、消失、新增的線段；端點只偏移 1 px 的（JPEG 重新編碼的誤差）只計數。確認列出的都落在這次修改的範圍內。
   - 線段改歸另一條線路（例如被併錯的引線改回正確線色）時，`verify.js` 也會報成 `⚠ 新合併`（例：`LG/R + G/R`）。這時用 `diff.js` 對照：如果被併進來的只是這次改了線色的那幾段，就是預期的結果，不是誤連。
   - 標了 `⚠` 的合併（線色不同，或有未標色的線被併入），每一筆都要用「接點」座標 crop 看原圖。
   - 同色的新合併也要抽查。
5. **找畫面缺口**：`node $S/labels.js x0 y0 x1 y1`。輸出中的 `#` 代表有墨水、但不屬於任何線路網，亮起時這裡會少一截。
6. **最終驗收**：`node $S/acceptance.js [x,y=x,y …]`，用 headless Chrome 跑真正的頁面。Node 和瀏覽器的 JPEG 解碼有差異，邊界值（例如 4 px 的缺口）結果可能不同，一律以 Chrome 為準。
   - Node 腳本的「線路網」數和 Chrome 的 `nets:` 算法相同，都排除 `staticAreas` 與元件名稱範圍；兩邊差幾個是解碼差異，差很多就是腳本和 `app.js` 不同步了。

**多張線路圖**
- 圖的清單在 `js/diagrams.js`。各圖的資料（底圖、元件、線色標註、人工修正）放在各自的 `data/<圖>/`，彼此獨立，修哪張圖就改哪張的 `fixes.js`。
- 腳本用環境變數 `DIAGRAM` 指定要處理的圖，預設 `PA12B`。
- 接線單元檔：PA12B 是 `wolf125-selections.json`，其他圖是 `wolf125-<圖>-selections.json`。

**工作目錄**
- 腳本的工作目錄是 `$WORK`，預設 `$TMPDIR/wolf-nets`。第一次使用前，要在裡面執行 `npm i jpeg-js@0.4.4`。
- `verify.js` 輸出的「修改前 N 段」是用目前 JSON 的 pick 計算的。新匯出的 JSON 每個單元只剩 1 個 pick，這欄就沒有參考價值。

## 圖面結構 → 修法
表中的參數門檻，以 `js/nets.js` 開頭的預設值為準。

| 圖面結構 | 症狀 | 修法 |
| --- | --- | --- |
| 線穿過接頭（三角形＋方框），可能還帶線色標籤 | 同色、同一軌的水平缺口，寬 58～130 px | 調 `bridgeMax`；限兩邊線色都已知且相同 |
| 線條上下錯位 2 px | 缺口在門檻內，卻被判成不同軌 | 調 `trackTol`；錯位 > 1 px 時，同樣限兩邊線色已知且相同 |
| 交會處有圓點但沒判到（圓點偏離中心） | T 字或交叉處斷開 | `dots` 加 `[x, y]` |
| 導線呈「ㄈ」形轉折（直線段短，兩支橫線朝同一側） | 直線段被當成接頭的框線排除 | `links` 加**沿實際走線的折線** |
| 導線呈 U 形轉折，底邊很細（約 1 px，沒被偵測成線段） | 兩支同色直線在底部斷開，底邊的像素標成 `#` | `links` 加沿 U 形走線的折線（例：脈波線圈下方引線 `[[2010, 1815], [2010, 1828], [2046, 1828], [2046, 1815]]`） |
| 短於 `minRun` 的下折 | 兩條橫線錯開約 10 px，中間的短直線在 `labels.js` 標成 `#` | `links` 加折線 |
| 接頭內部的跨接圓點，或併接（兩支腳併成一條） | 兩支腳和出線分屬不同線路網 | `links` 只放頭尾兩點，不要描進接頭符號 |
| 雙線外框的粗電纜（圓角、沒有線色標籤；例如電瓶到起動馬達、接地線） | 外框、內框的橫線和直線各成一段（例：1 條電纜變 4 段） | `cables` 加沿電纜中線的折線＋`code`；外框比預設寬時用 `half` 調整，接地電纜加 `ground: true` |
| 元件符號的筆畫（二極體、油錶線圈、元件內部迴路） | 符號被塗上線色，或兩支不同色的引線被併成一條 | `anchors.js` 在每段筆畫上加 `[x, y, 'X']`（非導線），被併錯的引線再補上正確線色；標註點要避開和其他線段的交叉處（同一點落在兩段時，會套到先找到的那段） |
| 純交叉、沒有圓點 | 看起來相連 | 不連，這是正確結果 |

## 常見錯誤
- **用通用規則處理「ㄈ」轉折**：試過「只要有一支臂是長導線，就不算框線」，結果：
  - 燈座方框把 L 線和 G 線接在一起。
  - 「脈波線圈」的線圈符號把頂端與下方兩支 G/W 引線接成一條（兩支引線分屬不同的線，不能透過線圈符號相連）。注意：下方引線經 U 形轉折接往 CDI 的那段是同一條線，已用 `links` 接上，這是正確的。
  - 標題底線被當成導線。

  加上平行邊檢查也擋不完，所以一律用 `links`。
- **放寬門檻卻不檢查線色**：放寬錯位容許、沒限線色時，大量未標色的碎線被合併，線路網從 587 掉到 542。放寬任何門檻，都要加上「兩邊線色已知且相同」。
- **`links` 只合併、沒描線**：邏輯上已經相連，但連接處的像素不屬於任何線路網，亮起時中間少一截。必須寫成沿實際走線的折線（起點 → 轉折點 → 終點，每段水平或垂直），沿線 ±3 px 的墨水才會被標進線路網。
- **`cables` 的寬度沒蓋住外框**：pick 點如果落在外框線上、但不在填色範圍內，驗收不會過。先量外框寬度，再設定 `half`。
- **只用 Node 驗收**：例如一處 4 px 的 T 字缺口，在 Node 會連上，在瀏覽器卻是斷開的。最後一定要跑 `acceptance.js`。
